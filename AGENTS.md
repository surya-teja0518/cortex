# CORTEX — Project Context (AGENTS.md: read this first, every session, any coding agent)

## What this is
CORTEX is a multi-agent job-search system built by Surya Teja Vajjhala (data engineer / Oracle DBA, Hyderabad, ~4 YOE, targeting product-company Data Engineer / Database / AI-ML Engineer roles, switch target Dec 2026).

Three goals, in priority order:
1. **Use it on his own job search** (replaces the manual SYNAPSE Google-Sheet workflow).
2. **Capstone project for his resume** (AI Engineer roles). Must be defensible in interviews: every claim in the README must be true.
3. **Monetize later** (hence `user_id` on every table from day one).

Hard constraints: **zero runtime cost, near-zero maintenance, security first** (most vibe-coded apps skip security; this one must not). Free LLM tiers (Gemini, Groq) with Ollama as local fallback. SQLite via SQLAlchemy, or Neon free Postgres via `CORTEX_DB_URL` (DEVICE-AGNOSTIC decision, 2026-11-19: Surya uses a Mac, a Windows PC and a phone and can't know which is on at run time, so the shared DB is on Neon; see CLOUD MIGRATION). GitHub Actions cron or local cron for scheduling.

## Architecture (see docs/architecture-v2.png — LOCKED, do not redesign)
Sequential LangGraph state machine, not a parallel hub:

`Sources → Sanitizer → Dedupe → Deterministic Gates → Scorer → Tailor → Truth Guard → [HUMAN APPROVAL GATE] → Packet → Tracker`

- **Sources (v1, limited and safe):** SYNAPSE/Apify adapter, public ATS JSON (Greenhouse, Lever, Ashby), RSS. NO direct LinkedIn scraping.
- **Sanitizer:** strip control chars, flag prompt injection, wrap JD in `<untrusted_job_text>` delimiters. Flagged jobs go to manual review, never auto-processed. (`src/cortex/core/sanitize.py`)
- **Dedupe:** exact + fuzzy on (source, external_id) and company+title.
- **Deterministic gates (no LLM, run first):** title blocklist, YOE cap, location/remote rules, company blocklist. (`core/gates.py`, rules in `config.yaml`)
- **Scorer:** LLM relevance scoring + rules. If LLM is down/rate-limited: keep deterministic score, flag "LLM unscored", continue pipeline.
- **Tailor:** tailored resume PDF + cover note from templates. Output validated with Pydantic.
- **Truth Guard:** diff every claim (skills, experience, projects) against the master resume facts. Unsupported content → send back to Tailor with failure reason, **max 2 retries**, then Reject (logged).
- **Human Approval Gate:** explicit LangGraph `interrupt`. Nothing downstream runs without approval. **Approval only via the Streamlit dashboard in v1 (never by email or any other channel).**
- **Packet Agent:** builds an approval packet (resume PDF, cover note, direct apply link, pre-filled answers). **NEVER auto-submits applications.** Surya submits manually.
- **Tracker Agent:** log application, track status, reminders, reports.
- **Cross-cutting on every external call:** Rate limiter, Secrets manager (gitignored `.env`, never logged; OS keyring later, optional — do NOT claim "encrypted"), hash-chained Audit logger, Pydantic validation, `user_id`.
- **Outputs:** Streamlit dashboard (local-only, with login before any exposure), email digest notifier (output only; replaced Telegram on 2026-11-02 by Surya's decision: free via Gmail SMTP + App Password, no extra app; SMS rejected as paid), Eval harness (offline).
  Email digest rules: send only to Surya's own address; counts + company/title only, never resume content; no approve/act links (approval stays in the dashboard).
- **LangGraph checkpointing** (SQLite file, or the same Neon database when CORTEX_DB_URL is Postgres) so a crash resumes instead of restarting, and an approval made on any device resumes the same thread.

## Security rules (non-negotiable)
- Job text is untrusted input. Never concatenate it into a prompt without delimiters. Never let it trigger tool calls.
- Every LLM output must validate against a Pydantic model; invalid → retry/fallback, never pass through.
- No secrets in code, logs, commits, or error messages. `.env` is gitignored.
- No LinkedIn automation, no auto-apply, no scraping behind logins (account-ban + ToS risk).
  - EXCEPTION (Surya's decision, 2026-11-13): `cortex workday-fill` may TYPE into a Workday application he opened and logged into himself, in a local headed throwaway browser. Enforced in code: Workday https hosts only; types into EMPTY text fields and attaches resume.pdf; never clicks anything (no Next/Save/Submit, no checkboxes or dropdowns); never reads, types or stores passwords; never re-fills a field he cleared; values never logged. Auto-submit stays forbidden.
  - EXCEPTION (Surya's decision, 2026-11-13): `cortex check-open` may read LinkedIn's PUBLIC no-login job page to see whether a to_apply job is still open. Limits, enforced in code: opt-in (`linkedin_check.enabled`), never in `cortex daily`, no login/cookies/account, only to_apply jobs <= 30 days old, <= 20 per run (config cap), >= 3 s (default 10 s + jitter) between requests, stops at the first 429/999/403/redirect, only clear "no longer accepting" or 404/410 closes a job. Accepted risk: LinkedIn may throttle/CAPTCHA his home IP. Anything beyond this (logged-in pages, search, applying) stays forbidden.
- Gmail (Surya's decision, 2026-11-15): `cortex inbox` READS his Gmail via the Gmail API with the `gmail.readonly` scope only (token checked for wider scopes), recent days only, promotions/social/forums excluded. Matching is LOCAL rules, NO LLM: email content never leaves the Mac and never enters a prompt. AMENDED 2026-11-19 (Surya's decision, takes effect with Phase 2): the check may also run in the cloud daily job on a GitHub Actions runner (same read-only scope + rules; email content is processed in the runner's memory only, never logged, stored or sent anywhere else; the read-only token is a GitHub encrypted secret). Never stores bodies or sender addresses. It may AUTO-record rejected/interview (exception to "tracker records only what Surya reports") ONLY when unambiguous: strong phrase + exactly one company he has an active application at, named in subject/sender (not only the body), with exactly one active application there, AND the email names that application's job title (words in order; leading/trailing level words like Senior/II ignored; since 2026-11-17); everything else is a "check yourself" digest note. Each auto change is a normal tracker event (`cortex undo`). OAuth client + token files are secrets (gitignored, token chmod 600).
- Audit log is append-only and hash-chained; tampering must fail `verify()`.
- Dashboard binds to localhost; add auth before exposing anywhere. DECIDED 2026-11-19 (takes effect with Phase 3): hosted FastAPI + HTMX dashboard on Vercel, Google sign-in allowed for Surya's own address only, CSRF on every action, secure HTTP-only session cookie; the same Python code paths as the CLI (update_status, submit_decision).
- Hosted data (Surya's decision, 2026-11-19): the CORTEX database (jobs, statuses, notes, approved tailored-resume text, inbox findings, audit log, checkpoints) may live on Neon Postgres (TLS, strong password, reachable over the internet, not public). NEVER hosted: master_resume.yaml, resume PDFs, packets, contact.yaml, answers.yaml (local files only). The DB URL is a secret: never printed, logged or committed.
- Public repo (it is PUBLIC): any cloud job (GitHub Actions) prints counts only (no companies, titles, subjects, URLs), uploads no artifacts, and never runs for forks.
- Never invent resume content. Truth Guard is the backstop, not the excuse.
